Metering

Metering runs a policy against a deterministic hidden-fault world, records everything the policy did, and measures the recording afterwards.

Get started Read the architecture

Welcome to the docs for Metering

Metering is a measuring instrument for the visible behavior of an agent harness. A harness is everything around a language model that decides what to do next, including the prompts, the tools, the retries, and the stopping rule. Measuring a harness honestly is hard, because most of what happens is invisible from the outside and easy to describe in flattering language. Metering starts from the opposite end by building one task where the correct answer is known in advance, then checking that the measurements come out right before any language model is involved.

The task is called the hidden-fault world. The controller picks one of eight faults and keeps it private. A policy receives the list of fault identifiers and a catalogue of diagnostic tests, spends actions to narrow the possibilities, proposes a repair, asks for verification, and finishes. Because the world is deterministic and its rules are published, anyone reading a saved run can recompute exactly what a policy could have known at every step. This is what makes the measurements checkable rather than merely reported.

Metering does not rank agents and does not produce an overall score. It answers one narrow question, which is whether the instrument can tell a careful diagnostic policy apart from a wasteful one using exact and replayable numbers. The rest of this page shows what those numbers look like and how the parts fit together.

Install and run it

Metering needs Python 3.11 or newer and uv. The runtime package has no third-party dependencies, so the checkout below is everything you need.

git clone https://github.com/muchmirul/metering.git
cd metering
uv run python -m metering calibrate

That command runs the full calibration suite, which executes every hidden state against every reference policy and then rebuilds each report from the files it just wrote. It finishes with the headline contrast between the two search strategies:

calibration passed: runs/calibration
balanced diagnostics: 24; sequential diagnostics: 35

What a run reports

Every report carries three readings that stay in separate columns. Keeping them apart matters because they answer different questions, and combining them would let a cheap failure look better than an expensive success.

Exact correctness

Four conditions are checked and reported one by one. The final repair must match the hidden fault, a verification must come after that repair, the policy must finish normally, and the budget must hold. Overall success needs all four.

Raw resource cost

Diagnostic observations, repairs, verifications, and total actions are counted separately, together with whether the run ran out of budget. Metering never adds them together into invented points.

Diagnostic information

The prior is uniform over eight states, so a run starts with three bits of uncertainty. The meter reports how many of those bits the delivered test results actually removed, and how many bits each observation was worth.

The calibrated contrast

The three reference policies all solve the task correctly, so correctness alone cannot separate them. What separates them is what they spent to get there. Balanced search asks questions that split the remaining candidates in half, which means every observation is worth a full bit. Sequential search checks one candidate at a time, so an early negative result removes very little. The table below is the measured output of the calibration suite, not an estimate.

PolicyCorrectDiagnostics per stateTotalBits removedBits per observation
Balanced search8 / 8[3, 3, 3, 3, 3, 3, 3, 3]2424.01.0000
Sequential search8 / 8[1, 2, 3, 4, 5, 6, 7, 7]3524.00.6857
Seeded random search8 / 8[4, 4, 4, 1, 4, 4, 4, 3]2824.00.8571

Each policy removes the same 24 bits in total, because each one ends up knowing the answer in all eight states. The efficiency column is the total bits divided by the total observations, which is the ratio of the sums rather than the average of the per-run ratios. Averaging the ratios would give a lucky one-observation run the same weight as a seven-observation run and would overstate how efficient the suite really was.

The system, from high level to low level

Metering is assembled from focused modules rather than one large framework. Each module has one responsibility and passes typed data to the next one, so a change in how a run is measured cannot reach back and change how the run was executed. The diagram reads from the command you type at the top down to the strict decoding rules that every layer shares at the bottom.

The boundary in the middle of the diagram is the design rule everything else follows. The controller hands the policy an immutable public instance and the observations delivered so far, and it never hands over the world object or the selected fault. Because of this, a policy cannot read the answer even by accident, and the only way it can learn anything is through actions that the trace records and the meters count.

The separation at the bottom matters just as much. Replay and the meters read files that are already written and hashed, so changing how a measurement is calculated cannot change a raw trace that was recorded earlier. This is what lets an old run be re-measured by newer code and still describe the same execution.

Two paths through one run

A run has an execution path and an interpretation path, and they never touch each other. During execution the controller and the world exchange typed values while the trace collects facts without judging them:

HiddenFaultSpec.default()  ->  HiddenFaultWorld holding one private fault
                                        ^
                     validate and apply  |  observation and raw cost
                                        v
Controller  -- public instance + history -->  policy.next_action(...)
Controller  <------------- one typed action --  policy.next_action(...)
     |
     +--> Event --> events.jsonl

Interpretation happens only after execution has ended and the files are closed. Replay reads them back, rebuilds the same controller state, and hands that state to the verifier and the meters:

manifest.json + events.jsonl + private reference.json
                        |
                        v
              strict offline replay
                        |
                        v
   exact verifier + resource meter + information meter
                        |
                        v
                   report.json

Because the second path never calls the policy or the world, a report can be rebuilt on a different machine, months later, from nothing but the saved files. The quickstart walks through doing exactly that.

What Metering deliberately leaves out

An instrument is only useful if its limits are stated as plainly as its results. The following boundaries are chosen rather than pending, and they are recorded inside every artifact so that a number cannot be quoted later without them.

  • The harness boundary is cooperative and in process. Metering cannot stop a callback that never returns, and it cannot survive a hard process exit, a segmentation fault, or an out-of-memory kill. It provides API non-disclosure and claims nothing about hostile code.
  • The information meter measures uncertainty removed by delivered results. It says nothing about whether a model understood or internally used what it was told.
  • Every reading is conditional on the declared world, policy, budget, and configuration. A result here is not a statement about harness quality in general.
  • Hashes and commitments detect corruption and accidentally mixed artifacts. They are not signatures, and they do not defend against someone who rewrites an entire artifact set coherently.

PLAN.md is the normative source for the accepted scope, the definitions, and the acceptance criteria that calibration enforces.

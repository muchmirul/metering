Guide

Quickstart

Run the calibration, execute one hidden fault, read what the meters produced, write your own policy, and rebuild a report from files alone.

Set up the checkout

Metering needs Python 3.11 or newer and uv. The runtime package has no third-party dependencies, and the test suite runs without a network connection or a model server.

git clone https://github.com/muchmirul/metering.git
cd metering
uv sync --extra test
uv run --extra test pytest -q

If the suite passes, the instrument matches its own executable contracts. The next step checks something stronger, which is whether the numbers it produces are the right numbers.

Run the calibration

Calibration is how Metering checks itself. It runs all eight hidden states against three reference policies whose costs are known in advance, deletes each report, rebuilds it from the saved files, and then compares the result against the expected readings.

uv run python -m metering calibrate
calibration passed: runs/calibration
balanced diagnostics: 24; sequential diagnostics: 35

Those two totals are the point of the exercise. Balanced search asks questions that halve the candidate set, so it identifies any of the eight faults in three observations and spends 24 across the suite. Sequential search checks one candidate at a time and spends 35. Both are correct, so a meter that could not separate them would not be ready to measure a policy whose behavior nobody knows in advance.

The default output directory is runs/calibration, and a non-empty directory is never overwritten. Passing --force replaces a directory only when it carries Metering's own marker file, so a mistyped path cannot turn calibration into a recursive delete. To write somewhere else, name it:

uv run python -m metering calibrate --output /tmp/metering-check

Every check, whether it passed or failed, is written to calibration.json in that directory. A failing suite still writes the file before it exits, so the reason stays available after the terminal has scrolled away.

Run one hidden fault

A single run is one call. Create a file called example.py in the checkout:

from metering import BalancedSearchPolicy, run_hidden_fault

result = run_hidden_fault(
    BalancedSearchPolicy(),
    hidden_fault_id="fault-3",
    run_dir="runs/example",
    run_id="example",
    action_budget=16,
)

print(result.succeeded)
print(result.report["resources"])

Then run it:

uv run python example.py
True
{'diagnostic_observations': 3, 'repair_actions': 1, 'verification_actions': 1,
 'total_actions': 6, 'action_budget': 16, 'budget_exhaustion': False}

The run directory must be new or empty, because a run owns the files it writes and will not merge itself into someone else's results. The hidden_fault_id argument sets controller-private truth and is never passed to the policy callback, so choosing it here does not tell the policy anything.

Read the report

The report is a plain dictionary with three independent readings. Correctness comes first, and it lists the four conditions separately so that a failure says which part went wrong:

{
  "selected_repair_matches_hidden_fault": true,
  "verification_occurred_after_final_repair": true,
  "harness_terminated_normally": true,
  "action_budget_was_respected": true,
  "overall_task_success": true
}

Repairing the right fault is not enough on its own. A run that repaired correctly but never verified afterwards, or that verified an outdated repair and then repaired again, fails a different condition than one that ran out of budget. Keeping the four visible is what turns a failure into a diagnosis instead of an unexplained false.

The information reading describes how the uncertainty actually fell. Eight equally likely faults carry three bits, and each entry in the progression shows what one delivered result removed:

{"diagnostic_index": 1, "test_id": "split-1", "positive": true,
 "candidate_count_before": 8, "candidate_count_after": 4,
 "uncertainty_before_bits": 3.0, "uncertainty_after_bits": 2.0,
 "uncertainty_removed_bits": 1.0}

Only delivered diagnostic results count here. Choosing a test is an intervention rather than evidence, so it removes nothing by itself, and repair, verification, and finish carry no diagnostic content at all. This is why repeating a test you already ran shows up as a real observation that removed zero bits, which is exactly the waste the meter exists to make visible.

Read the trace

The trace records what happened, one canonical line per step, with no interpretation mixed in. Reading the run above gives a complete picture of the interaction:

0  run_started  action_budget 16, artifact_set_id, full public instance
1  interaction  diagnose split-1  ->  positive true
2  interaction  diagnose split-2  ->  positive true
3  interaction  diagnose split-3  ->  positive false
4  interaction  repair fault-3    ->  repair_applied fault-3
5  interaction  verify            ->  verification_acknowledged
6  interaction  finish            ->  finish_accepted
7  termination  reason normal_finish, actions_used 6, budget 16

Notice what step 5 does not say. Verification returns an acknowledgement with no result in it, so the policy learns that verification happened and nothing more. If it returned pass or fail, a policy could call it repeatedly to identify the fault for free, and the resource meter would never see the questions it was really asking.

The four artifacts

A finished run directory holds four files, and each one has a different role and a different trust boundary.

runs/example/
├── manifest.json
├── events.jsonl
├── reference.json
└── report.json
FileWrittenContents
manifest.jsonBefore the policy runsThe public instance, the world specification, the budget, the policy descriptor, implementation provenance, the artifact identity, and an opaque commitment to the private truth.
events.jsonlDuring the runAppend-only canonical facts with contiguous step numbers and per-event raw costs.
reference.jsonAfter the policy endsThe selected fault, the commitment nonce, the final private world state, and hashes binding the exact manifest and event bytes.
report.jsonLastCorrectness, raw resources, diagnostic information, the declared scope, and hashes of all three inputs it read.

The order is deliberate. The manifest commits to the hidden fault before the policy gets its first callback, and the reference reveals that fault only after the policy can no longer act on it. Replay recomputes the commitment from the revealed values, which means a plausible hidden fault cannot be substituted after the fact. Keep reference.json outside the policy boundary while a run is in progress, because it is the one file that contains the answer.

Write your own policy

A policy is any object with two methods. next_action receives the public instance and every observation delivered so far, and returns exactly one typed action. descriptor returns a JSON-compatible declaration that goes into the manifest, so a reader can tell later how the run was configured.

from metering import Diagnose, Finish, Repair, Verify, run_hidden_fault
from metering.policies import remaining_candidates


class FirstUnusedSplitPolicy:
    name = "first-unused-split"
    version = "1"

    def descriptor(self):
        return {
            "name": self.name,
            "version": self.version,
            "configuration": {"order": "public_catalogue_order"},
            "seed_policy": {"kind": "none"},
        }

    def next_action(self, instance, observations):
        kinds = [getattr(item, "kind", "") for item in observations]
        if "repair_applied" in kinds:
            return Finish() if "verification_acknowledged" in kinds else Verify()

        candidates = remaining_candidates(instance, observations)
        if len(candidates) == 1:
            return Repair(candidates[0])

        used = {item.test_id for item in observations
                if getattr(item, "kind", "") == "diagnostic_result"}
        remaining = set(candidates)
        for test in instance.diagnostic_tests:
            positives = remaining & set(test.positive_fault_ids)
            if test.test_id not in used and 0 < len(positives) < len(remaining):
                return Diagnose(test.test_id)
        return Repair(candidates[0])


result = run_hidden_fault(FirstUnusedSplitPolicy(), "fault-6", "runs/mine")
print(result.report["diagnostic_information"]["uncertainty_removed_per_diagnostic_observation_bits"])

The helper remaining_candidates does the reasoning a policy is entitled to do. It filters the fault list using delivered diagnostic outcomes and the published observation model, and it ignores repair and verification results because those are not diagnostic evidence. Writing that logic yourself is fine, and using the helper keeps a policy honest about what it was allowed to know.

A policy that returns something other than a typed action, or that names a test outside the catalogue, is not quietly corrected. The controller records a protocol error, charges it one unit of budget, and stops the run. A descriptor that is missing a field is rejected before the run starts at all, because a result nobody can reproduce is worse than no result.

Rebuild a report offline

A report is a calculation over saved files, so it can be thrown away and rebuilt at any time. Delete it and ask for it back:

rm runs/example/report.json
uv run python -m metering report runs/example
regenerated runs/example/report.json for run example

Replay does not call the policy and does not call the world. It reads the three raw files, rebuilds the controller state that must have produced them, and checks the schemas, the artifact identity, the private commitment, every transition, every recorded cost, and the exact bytes of each input. Only when all of that passes does the new report atomically replace the old one.

The failure behavior is the part worth testing yourself. Flip one recorded diagnostic outcome in events.jsonl and try again:

report regeneration failed: diagnostic outcome contradicts the generated instance

The command exits with status 1 and the previous report.json is left exactly as it was. A corrupt run therefore cannot quietly replace a good measurement with a wrong one, which is what makes a rebuilt report worth the same as the original.

When a run goes wrong

Three failure paths are part of the contract rather than accidents, and each one ends with an explicit termination record instead of a silent stop.

What happenedTermination reasonWhat the trace shows
The policy returned an action the world rejectsinvalid_actionA protocol_error event carrying the code and the attempted action, charged one unit of budget, then termination.
The policy never asked to finishbudget_exhaustedExactly as many actions as the budget allows, and no further callback.
next_action raised an exceptionharness_crashTermination with no interpretation of the exception text.

A valid Finish() spent as the last budgeted action counts as normal success rather than exhaustion, because the policy did finish and the budget did hold. Two failures are outside this boundary entirely. Metering cannot stop a callback that never returns, and it cannot recover from a hard process exit, so it does not claim either one.

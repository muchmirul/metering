Theory beside implementation

Theory and scope

Metering is a focused experiment with a larger purpose: define measurements that remain meaningful before adding language models, external tools, and real repositories. This page explains each idea beside the code that implements it.

Why measurement comes first

The idea

A real agent run mixes many causes: the model, prompt construction, tools, retries, memory, verification, stopping logic, and luck. A single success rate or composite score can hide which part helped and which part failed.

Metering begins with a world where every answer and cost can be derived in advance. If the instrument cannot distinguish an efficient diagnostic policy from a wasteful one here, there is no reason to trust it on a system whose behavior is harder to inspect.

This is calibration in the ordinary measurement sense. Test the ruler against known lengths before using it on an unknown object.

Implemented in calibration.py

EXPECTED_BALANCED_DIAGNOSTICS = [3] * 8
EXPECTED_SEQUENTIAL_DIAGNOSTICS = [1, 2, 3, 4, 5, 6, 7, 7]
INITIAL_UNCERTAINTY_BITS = 3.0

The expected values are stated independently of a measured run. run_calibration executes the policies, rebuilds every report, and fails if the measured values do not match these consequences of the world definition.

A finite hypothesis space

The idea

A “fault” is not broken source code in the current project. It is one hidden label in the finite set

F = {fault-0, fault-1, …, fault-7}.

The prior is uniform, so each fault initially has probability 1/8. A diagnostic test publishes the states where its answer would be true. Once a result arrives, the policy keeps the states consistent with that result and rejects the rest.

Because the prior is uniform and the tests are deterministic, the posterior remains uniform over the surviving candidates. This is a particularly simple Bayesian update, not a general noisy inference engine.

Implemented in hidden_fault.py and policies.py

Realized information in bits

The idea

A uniform choice among n candidates has entropy

H(n) = log₂(n) bits.

Eight candidates therefore start at log₂(8) = 3 bits. If one delivered result narrows n candidates to k, the information exposed by that result is

ΔH = log₂(n) − log₂(k) = log₂(n/k).

The meter calculates the reduction that actually occurred on this run. It does not calculate expected mutual information before a test is chosen, and it does not claim that a model understood the result. Choosing a test is an intervention; receiving its outcome is evidence.

Implemented in report.py

def _entropy(candidate_count: int) -> float:
    if type(candidate_count) is not int or candidate_count < 1:
        raise ReportError(
            "an impossible diagnostic result eliminated every state"
        )
    return math.log2(candidate_count)
before_uncertainty = _entropy(before_count)
after_uncertainty = _entropy(len(candidates))

"uncertainty_removed_bits": (
    before_uncertainty - after_uncertainty
)

Only Diagnose interactions enter this loop. A repeated result still costs one observation but leaves the candidate set unchanged, so it removes exactly zero additional bits.

Binary decision trees

The idea

Each diagnostic has two outcomes, so a depth-d decision tree has at most 2ᵈ leaves. Distinguishing eight faults requires

2ᵈ ≥ 8, so d ≥ 3.

Balanced search reaches that lower bound with 8 → 4 → 2 → 1. Sequential search asks whether the answer is one particular fault, then another. It remains correct, but its depths are [1, 2, 3, 4, 5, 6, 7, 7].

Running every state matters. A sequential policy can get lucky and find fault-0 in one observation. Across the complete uniform world, luck cancels out and the total cost is 35 rather than 24.

Implemented in policies.py

_, selected = max(
    choices,
    key=lambda item: (
        min(
            len(candidate_set.intersection(
                item[1].positive_fault_ids
            )),
            len(candidate_set.difference(
                item[1].positive_fault_ids
            )),
        ),
        -item[0],
    ),
)

BalancedSearchPolicy maximizes the minimum side of the next split. SequentialSearchPolicy instead takes the first remaining candidate and finds its singleton test:

candidate = candidates[0]
for test in instance.diagnostic_tests:
    if test.positive_fault_ids == (candidate,):
        return Diagnose(test.test_id)

A harness as an observable computation

The idea

For this experiment, a harness is a policy that maps the public instance and its observation history to one next action:

π(public instance, history) → action.

The action enters a deterministic state machine. The controller validates it, applies it through the world, charges its raw cost, records the transition, and either asks again or terminates. This operational definition is deliberately narrower than informal claims about reasoning.

The trace captures what the harness did. It does not attempt to inspect hidden thoughts or infer whether a model internally used the information it received.

Implemented in HarnessPolicy and Controller

def next_action(
    self,
    instance: PublicInstance,
    observations: Sequence[Observation],
) -> Action:
    """Choose one typed action from public input
    and delivered observations."""
output = self.policy.next_action(
    public, tuple(self._observations)
)
validation = self.world.validate_action(output)
observation, cost = self.world.apply(action)
self._actions_used += cost.total_actions
self._observations.append(observation)
self.trace.append(...)

The final ellipsis abbreviates construction of the recorded Event; the complete event payload and cost are visible in Controller.run.

Verification is not a hidden diagnostic

The idea

If verification returned pass or fail to the harness, the harness could guess each fault and verify repeatedly. It would learn the hidden state through a channel that the diagnostic meter did not count.

Metering therefore keeps the result controller-private. The harness receives only an acknowledgement that verification happened. Offline correctness later checks whether a verification occurred strictly after the final repair, so changing a repair also makes an older verification stale.

This information-flow rule has a clear purpose: all diagnostic evidence must pass through the declared, metered diagnostic channel.

Implemented in HiddenFaultWorld.apply and _correctness_report

passed = self._selected_repair == self._hidden_fault_id

)
verified_after_final_repair = (
    state.final_repair_step is not None
    and any(
        step > state.final_repair_step
        for step in state.verification_steps

)

Correctness, cost, and information stay separate

The idea

A cheap failure is not better than an expensive success merely because somebody chose favorable weights. Metering therefore refuses to collapse unlike quantities into one score.

Correctness answers whether the declared task was completed. Resource fields count diagnostics, repairs, verifications, and total actions. Information reports how much uncertainty the diagnostic results removed. The reader may compare these columns, but the instrument does not invent an exchange rate between them.

At suite level, efficiency is a ratio of sums. This gives every paid observation equal weight:

efficiency = total bits removed / total diagnostics.

The complete eight-state suite also has a natural zero-cost reference. Kraft's equality gives a minimum total leaf depth of 24 for a binary tree with eight leaves:

excess observations = total diagnostics - 24.

This second value is suite-only. A single leaf may be reached in one observation, so subtracting a worst-case depth from one run would produce a meaningless negative value. General aggregation remains available for any collection, but its excess field is null unless it contains exactly eight successful reports. Calibration separately proves that those eight reports cover every state under one reference policy; a report cannot prove its own private state coverage without leaking the answer.

Averaging the per-run efficiencies would give a lucky one-observation run the same influence as a seven-observation run. The implementation instead divides the 24 total bits by the 35 observations purchased by sequential search and reports 11 observations above the binary-tree minimum.

Evidence is recorded before it is interpreted

The idea

A measurement should not change the computation it measures. Metering writes the public manifest first, appends raw events while the policy runs, writes the private reference after the final callback, and builds the report last.

Offline replay reconstructs the legal state transitions from those saved files. Strict schemas, contiguous steps, canonical JSON, hashes, and a salted commitment detect corruption and accidental artifact mixing. A valid report can be regenerated without executing the harness or the world again.

The hashes are integrity checks, not signatures. They do not stop someone from coherently rewriting an entire artifact set.

Implemented in runner.py, replay.py, and regenerate_report

write_json_atomic(paths.manifest, manifest)

with TraceWriter(paths.events, sync=sync_trace) as trace:
    Controller(...).run()

write_json_atomic(paths.reference, reference, private=True)

write_json_atomic(paths.report, report)
report = build_report(
    manifest,
    read_events(paths.events),
    reference,
    artifact_bytes={...},
)
write_json_atomic(paths.report, report)

regenerate_report performs the final atomic write only after strict replay and every integrity check have succeeded.

What calibration proves

The idea

Calibration covers every hidden state instead of sampling one. Balanced and sequential policies must both succeed, balanced search must spend exactly 24 diagnostics, and sequential search must spend exactly 35. Each successful run must remove all three initial bits.

The suite also checks seeded replay, invalid output, budget exhaustion, an ordinary callback exception, finishing exactly at the budget boundary, offline report regeneration, and rejection of a contradictory recorded outcome.

Passing these checks shows that this implementation agrees with its controlled model. It does not prove that the model represents every real harness task.

Implemented in run_calibration

primary = _run_reference_policies(suite, seed)
aggregates = _check_expected_readings(suite, primary)
replays = _check_seeded_replay(
    suite, seed, primary["seeded_random"]
)
controller_check_runs = _check_termination_paths(suite)
_check_corruption_is_detected(
    suite, primary["balanced"][0]
)

The command writes every check to calibration.json, including failures, before returning a nonzero exit status.

Which harnesses can be measured today?

The supported boundary is precise. Metering directly accepts a cooperative Python object with a finite descriptor and a next_action method. The object runs inside the Metering process, receives the public hidden-fault instance and delivered observations, and returns one typed action. It must return normally and must solve this specific hidden-fault protocol.

HarnessCurrent supportWhat is required
Built-in reference policiesDirectNothing; they implement HarnessPolicy.
Custom Python diagnostic controllerDirectImplement descriptor() and next_action(), return typed actions, and use a new run directory.
Python wrapper around a model or remote serviceManual adapter onlyThe user must translate public inputs into requests and responses back into Metering actions. Metering supplies no adapter or model provenance capture.
Agent CLI, HTTP harness, or another processNot directAn external protocol and process controller would need to be designed and implemented first.
Coding, browser, shell, or repository agentNot supportedThose tasks need a new controlled world, action vocabulary, observation model, costs, and calibration cases.
Hostile or potentially nonreturning callbackNot supportedThe current boundary has neither isolation nor an enforced timeout.

The actual contract

A model-backed experiment is possible only if someone writes a local object satisfying this contract. That adapter remains responsible for prompts, model calls, parsing, retries, and reproducibility. Metering sees only the typed action it returns.

This does not turn the boundary into a sandbox. The contract prevents accidental disclosure through the documented API; it does not defend against code that deliberately inspects process memory, reads unrelated files, or refuses to return.

Implemented in HarnessPolicy and declared by runner.py

"execution_boundary": {
    "kind": "cooperative_in_process",

The result must not be oversold

Metering currently calibrates measurements in one deterministic eight-state world. It does not yet evaluate general agent or coding-harness quality.

  • There is no external harness protocol, model adapter, subprocess controller, timeout enforcement, tool runner, or repository task.
  • The controller cannot stop a callback that never returns or recover from a hard exit, segmentation fault, out-of-memory kill, or interpreter failure.
  • Information means realized posterior-entropy reduction from delivered catalogue results. It does not mean comprehension, reasoning quality, trust, memory, or internal use.
  • The entropy calculation is valid for the declared uniform prior and deterministic observation table. A different prior or noisy world requires a different validated calculation.
  • Results are conditional on this world, catalogue, policy descriptor, configuration, and action budget. They do not establish universal harness quality.
  • Correctness, raw costs, and information remain separate. Metering has no combined score, ranking, or leaderboard.
  • Hashes and commitments detect corruption and accidental mixing. They provide neither authentication nor protection from coherent malicious rewriting.

Every report carries this scope block, and every manifest declares hostile_code_sandbox_enforced: false. The limitations therefore travel with the result instead of living only on this page.

These are not details hidden in a disclaimer. They define what the measurements mean. Extending the project responsibly requires a new boundary or world to come with equally explicit semantics, known calibration cases, tests, artifacts, and compatibility rules.

Developer guide

Read this before changing execution, measurement, artifact, or replay behavior.

The theory and scope guide explains why each measurement exists and places the relevant mathematics beside the code that implements it. This page starts from that contract and follows the implementation layer by layer.

The stack

Metering is built as a sequence of layers rather than as one framework with plug-in points. Each layer depends only on the layers below it, which means you can read the code top down and never need to jump back up to understand what a value means. The diagram shows the full stack, from the command you type down to the strict decoding rules that everything shares.

Layer by layer

The sections below walk the same stack in order, saying what each layer is responsible for and what it deliberately refuses to do.

Entry points

__main__.py exposes two commands and nothing else. metering calibrate runs the self check, and metering report DIR rebuilds one report from saved files. Both return a non-zero exit status on failure and print the reason to standard error, so they compose with a shell script or a continuous integration job. The Python entry point run_hidden_fault is the equivalent for a single run.

Calibration

calibration.py is the layer that decides whether the instrument is trustworthy. It runs eight hidden states against three reference policies, rebuilds every report from disk, and then compares the readings against values that follow from the world definition rather than from the code that produced them. It also exercises the four termination paths and confirms that flipping one recorded outcome makes replay fail. If any check fails, the summary is written to calibration.json before the command exits, so the reason survives.

Controller

runner.py owns the state machine. It requests one action at a time, charges every attempt to the budget including invalid ones, routes valid actions through the world, appends one event per step, and records exactly why the run stopped. The controller never repairs malformed harness output, because doing so would hide a defect in the thing being measured. It also never passes the world object or the private truth into a callback.

Harness boundary and world

This is the layer where the design rule lives. policies.py defines the callback that receives an immutable public instance and the observations delivered so far, and hidden_fault.py defines the world that holds the selected fault. The two never meet directly, so the only channel between them is a typed action going one way and a typed observation coming back, and every crossing costs budget and appears in the trace.

Protocol and canonical bytes

events.py defines four actions, four observations, the per-action raw cost, and the canonical event. trace.py gives every artifact exactly one valid byte representation, which is what makes a SHA-256 hash meaningful, since two readers of the same values always produce the same bytes. binding.py hashes the selected fault together with a fresh nonce so the manifest can commit to the truth without revealing it.

Replay and meters

replay.py rebuilds the controller state from files and refuses anything inconsistent, and report.py turns that state into three separate readings. Neither one calls a policy or a world, which is what lets an old run be re-measured by newer code and still describe the same execution. It also means a change to a meter can never change a raw trace, so a measurement is always a claim about evidence that already exists.

Schema

schema.py sits underneath everything and has no dependencies inside the package. It holds the schema versions, the event and termination vocabulary, and one set of strict field checks that every layer above reuses through StrictFields. Binding the checks to a caller-chosen error type is what lets a malformed action surface as EventError and a malformed manifest as ReportError while the rule itself is written once.

Execution semantics

A policy selects one typed action from public input and the observations it has already received:

def next_action(self, instance, observations):
    ...

The callback returns exactly one of Diagnose(test_id), Repair(fault_id), Verify(), or Finish(). Plain mappings are not converted into actions, because an untyped value arriving from a harness is a defect worth recording rather than a formatting difference worth fixing.

Action lifecycle

For one valid non-finish action, the controller does the following in order:

  1. asks the policy for one action;
  2. validates the action against the current world state;
  3. applies it to the world and receives an observation and a raw cost;
  4. charges the cost against the budget;
  5. records the typed action, the typed observation, and the cost as one event;
  6. includes the observation in the history for the next callback.

A valid Finish() records normal termination and produces no further callback.

Verification privacy

Verify() is valid only after a repair has been selected. Its public result acknowledges that verification happened and says nothing about whether the repair matches private truth. The outcome is recorded privately and appears only in the offline report. If verification returned pass or fail, a policy could call it repeatedly to identify the fault, and the resource meter would count cheap verifications instead of the diagnostics that were really being performed. A later repair also makes an earlier verification stale, so the verifier requires a verification strictly after the final repair.

Budget boundary

Every attempt consumes one total-action unit, including an invalid attempt and including Finish(). The boundary behavior is worth stating precisely:

  • A valid Finish() spent as the last budgeted action terminates normally, because the policy did finish and the budget did hold.
  • A non-finish action at that same boundary is recorded first, and the run then terminates as budget exhaustion.
  • No callback is made once the budget is reached, so a policy cannot observe the boundary and react to it.

Failures and process limits

An invalid action produces a typed protocol-error event carrying the rejection code and the attempted action, then terminates the run. An ordinary exception from next_action is recorded as a harness crash, and the exception text is deliberately neither stored nor interpreted, since a meter that read error strings would be measuring prose.

The boundary is cooperative and in process. Metering cannot stop a callback that never returns, and it cannot recover from a hard process exit, a segmentation fault, an out-of-memory kill, or an interpreter failure. Process isolation is deferred rather than partially implemented, because a partial sandbox would invite a claim the code cannot support.

Artifact lifecycle

The order in which a run writes its files is part of what the artifacts prove. The manifest commits to the hidden fault before the policy gets its first callback, and the reference reveals that fault only after the policy can no longer act on it.

Integrity and replay

Canonical encoding

JSON documents use sorted keys, compact separators, UTF-8, and a trailing newline, and a trace uses one canonical object per line. Strict decoders reject duplicate keys, unexpected fields, non-finite numbers, and Boolean or floating-point substitutes for integer fields. Rejecting rather than resolving matters because either behavior would let two readers disagree about what a file says, and a hash over an ambiguous file proves nothing.

Artifact identity

The caller-controlled run_id is only a label. Every execution also receives a controller-generated artifact_set_id, which is a fresh UUID4 that no caller can influence. Because of this, files from two executions cannot be mixed accidentally even when their run labels are identical, and replay notices immediately when they are.

Private commitment

Before the first callback, the controller hashes the artifact identity, a fresh nonce, and the complete generated-instance identity, and publishes only the digest in the manifest. After the run, the reference reveals both the fault and the nonce, and replay recomputes the digest. Publishing a bare hash of one of eight faults would be worthless, since a reader could hash all eight and compare. Holding the nonce back is what keeps the truth committed and undisclosed at the same time.

What the checks do not cover

Hashes and commitments detect corruption, staleness, and accidentally mixed artifacts. They are not signatures, and they do not defend against someone who rewrites an entire artifact set coherently. Treat them as a check on accident rather than on intent.

The replay checklist

replay_trace runs these checks in this order, and the order is deliberate. Semantic checks come before byte comparisons so that a contradictory observation is reported as trace corruption rather than as an unexplained hash mismatch.

  1. exact manifest and reference schemas, including the declared execution boundary and reproducibility claims;
  2. controller, verifier, and meter version compatibility with the installed implementation;
  3. artifact-set identity and the private-truth commitment;
  4. contiguous step numbers and stable run, world, and instance identity on every event;
  5. legal transitions, correct observations, correct per-event costs, and a consistent termination reason;
  6. the replayed private final state against the recorded one;
  7. exact canonical bytes for all three inputs and the manifest and event hashes bound by the reference.

The package release version is recorded as provenance only. Compatibility is decided by the component versions, because those are the parts whose behavior a replay actually depends on. A behavioral or interpretive change must bump the component version that replay uses as its gate.

The current implementation records meter version 2, controller version 1, and verifier version 1; all artifact schemas remain at version 1. Meter version 2 adds the suite-level excess-observation interpretation without changing per-run schema shape or raw execution semantics. Strict replay does not reinterpret meter-v1 artifacts: use a v1-compatible checkout for those runs.

Extending Metering

Where a change belongs follows from the stack. Adding a policy means writing one class at the harness boundary and nothing else, and the run it produces is comparable with the reference policies because the world and the meters did not move. Adding a measurement belongs in report.py, and it needs its own calibration evidence, which means a case where the expected reading follows from the world definition rather than from the new code.

Changing the world, the schemas, or the protocol is a larger decision. Those changes alter what a saved artifact means, so they need matching updates to PLAN.md, the tests, the implementation, and the user documentation, plus a statement about whether existing runs remain readable. When those four sources disagree, stop and name the disagreement instead of picking whichever one is easiest to change.

Testing and releases

Development environment

uv sync --extra test

The runtime package and the static documentation have no third-party dependencies.

Validate a change

uv lock --check
uv run --extra test pytest -q
python -m compileall -q src tests
uvx ruff check --select E9,F63,F7,F82 src tests

The suite covers the fixed catalogue, reference-policy costs, information calculations, complete-suite bound applicability, budget behavior, crash records, strict schemas, artifact mixing, private-truth binding, verification privacy, offline replay, force safety, and tag-derived package versions. It runs without a network connection or a model server.

Run a fresh calibration

uv run python -m metering calibrate --output /tmp/metering-check

Run this for any change to execution, traces, reports, policies, or calibration itself. The expected totals are 24 diagnostics for balanced search and 35 for sequential search. Seeded-random output depends on the seed but is deterministic for a given one.

Check offline regeneration

uv run python -m metering report PATH_TO_RUN_DIRECTORY

Run this for any change to replay. Delete or copy a generated report.json first, then confirm that the rebuilt file matches the original. Also confirm the negative case, since a corrupt input must fail and leave the previous report in place.

Preview the documentation

The documentation is static HTML with no build step, and GitHub Pages deploys the same files directly from docs/.

python -m http.server --directory docs 8000

Releases and compatibility

Numeric Git tags and GitHub Releases are the source of the package version, and setuptools-scm derives the installed value:

uv run python -m metering --version

See RELEASING.md for the process. Before changing a schema, a component version, an action, an observation, an artifact field, a policy descriptor, or a replay rule, state explicitly whether existing runs remain readable and what a user has to do if they do not.
